01

How I think about AI products

i. Evaluate before you ship

Define "good enough" with a metric, not a vibe. A feature that answers differently every run needs a bar you can measure it against — and a way to know when it clears.

ii. The discipline of no

Great PMs are defined as much by what they kill as what they ship. I decline the request that optimizes the wrong metric — even under the pull of urgency.

iii. Auditability over raw speed

When errors have consequences, I choose the architecture I can inspect and debug over the one that's merely fastest. Trust is built in the logs.

iv. Graceful failure is a feature

Agents will hit their limits. A confident hand-off when the model lacks context beats confident nonsense every time — and it's what earns enterprise trust.

Case study 00 · Built in the open · Runnable in 10 seconds

Sentinel — a reliability gate for high-stakes AI agents

64.7% → 94.1%
Why
The case studies below are work I led on someone else’s product. This one is mine, and you can check it rather than take my word for it. github.com/rickyric395/sentinel-eval
What it does
Runs 17 tiered scenarios — happy path, edge, adversarial — against an agent under test. Each reply is scored by an LLM judge against that scenario’s own rubric and independently cross-checked by deterministic assertions. Three runs per scenario give a pass rate, not a verdict. A four-rule gate then exits non-zero when a prompt change makes things worse.
Decisions
The baseline is promoted by hand on purpose: if the gate could update its own baseline, a slow slide in quality would never trip it. Fixture keys are content-addressed, because keying on scenario id meant editing a prompt and silently replaying the old prompt’s answers as a fresh result — a bug caught before shipping that would have produced real-looking fake numbers.
Result
204 recorded turns. A tightened prompt moved the suite from 64.7% to 94.1% — +29.4 points from prompt work alone — with critical failures going 2→0 and judge/check disagreements 6→0. An earlier synthetic test suggested +58.8; that number was never real, and no attempt was made to widen the measured one.
The finding
The naive prompt passed every adversarial scenario it was built to resist — jailbreak, PII disclosure, policy boundary, all 100% — and failed the mundane ones: writing down a callback time (0%), reading a garbled transcript (0%), handling an angry customer (0%). Both of the tightened prompt’s remaining failures are still on the happy path. Reliability work aimed at attacks would have missed the real problem.
Cost vs quality
A second experiment sweeps two prompts across two models with the judge model pinned, so the agent model is the only variable. The tightened prompt on the cheaper model beats the naive prompt on the expensive one on every axis at once — 86.3% vs 78.4%, at 7.7× less cost and 2.7× lower latency. Buying a better model was the more expensive way to get less. Read the writeup →
What broke
Re-recording an identical configuration moved the score 13.7 points, so the headline “+29.4” did not reproduce — inside one sweep the same change is worth +11.8. The direction held; the magnitude didn’t. Both numbers are published and the flattering one wasn’t quietly swapped, because a suite that reports a point estimate without a spread is claiming more than it can support.
Guardrails & language
Third experiment: the identical suite with one variable changed — the customer writes Roman-script Hinglish, the way much of India actually types. The suite falls from 94.1% to 62.7% and critical failures go from 0 to 3. A prompt injection blocked 100% of the time in English gets through two times in three in Hinglish; PII and policy-boundary guardrails degrade the same way. Guardrails written and tested in one language did not transfer. Read the writeup →
Try it
Clone it and run npm test. The whole suite replays from committed fixtures in about ten seconds — no API key, no cost. Every figure in the README is generated from a recorded run; the repo refuses to print one that isn’t.

Case study 01 · Voice AI · Trust

Making a voice receptionist trustworthy enough to front real calls

27% → <12%
Problem
A voice agent that hallucinates erodes the very trust it needs to answer inbound calls autonomously. "Sounds fine" wasn't a bar we could ship on.
Approach
Manually reviewed transcripts, defined an accuracy metric, rewrote prompts into a constrained, voice-optimized format, and measured before/after on the same 500+ transcript set.
Judgment
Chose a cascading STT→LLM→TTS pipeline for auditability over a faster speech-to-speech black box — because I had to be able to explain why it said what it said.
Impact
Cut hallucination 27%→<12%; added a fallback-provider failover that held 100% voice uptime through a third-party TTS outage.

Case study 02 · Scale · The discipline of no

78% autonomous containment — without runaway token cost

78%+ contained
Problem
WhatsApp chats never formally "end," so naive context handling meant unbounded token cost as the platform scaled across orgs.
Approach
Rejected unbounded context; designed configurable inactivity-based session closure plus summary-memory that rehydrates when a customer returns days later.
Judgment
The discipline of no — protected platform scalability over the "keep everything" instinct, trading perfect recall for bounded, predictable economics.
Impact
78%+ of chats resolved autonomously with token cost held in a predictable envelope.

Case study 04 · Experimentation · Impact

+40% purchase conversion via voice & prompt A/B

+40% conversion
Problem
Which agent configuration actually makes a business decide to buy the AI receptionist?
Approach
Multivariate tests of voice IDs + prompts by business subcategory across 1,000+ healthcare businesses; measured in SQL/Metabase, validated before/after.
Judgment
Let the data pick the winner, then scaled the winning config — rather than trusting a hunch about what "sounds better."
Impact
Winning configuration lifted product purchase conversion ~40% over the prior setup.
